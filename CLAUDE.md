Bajo ninguna circunstancia debes añadir firmas de autoría, marcas de agua, ni trailers en los commits (como `Co-Authored-By: Claude` o `Generated by AI`). Tampoco debes incluir tu nombre en comentarios de código (`@author`), encabezados de archivos o documentación. ## Reglas del proyecto

Esta sección es la que manda sobre CÓMO trabajar en este repo. Es distinta de [`docs/ESTADO.md`](./docs/ESTADO.md), que es deliberadamente descriptivo (reporta hechos verificados en el código) y no prescriptivo — las reglas viven aquí, no ahí, para que una sesión que lea `CLAUDE.md` (que se carga siempre) no dependa de haber leído también `docs/ESTADO.md` para saber qué está permitido hacer.

### Flujo de ramas

Git Flow formalizado: todo desarrollo nuevo nace de una rama dedicada `feat/...` o `fix/...` (o `chore/...` para tareas de mantenimiento como esta) creada desde `develop` sincronizado. **Prohibido commitear directo a `main`/`develop`.** Flujo normal: rama → `npm run build` OK → commit → push → PR → merge. `staging` (conectada al despliegue de Vercel) suele quedar varios commits atrás de `develop`/`main` — no asumir que refleja el estado más reciente sin comprobarlo.

### Reglas de i18n

1. **`src/i18n/routes.ts` es la única fuente de verdad de rutas.** Agregar la clave `en` a una entrada activa automáticamente el `LanguageSwitcher`, el fallback de Navbar/Footer, y los alternates del sitemap — nada más que tocar en esos tres sitios.
2. **En archivos `.astro`, nunca se accede a `.es`/`.en` de un campo `Localized<T>` de forma literal.** Siempre `localize(campo, locale)`, con `locale = Astro.currentLocale === "en" ? "en" : "es"`. Aplica incluso en páginas que todavía no tienen versión en inglés — un `.es` hardcodeado compila igual y falla en silencio el día que se traduzcan.
3. **Las islas de React reciben las cadenas ya traducidas como props planas (`string`), nunca el objeto `Localized<T>` ni el diccionario completo.** Cero Context, cero provider, cero hook de i18n en React — cada isla se hidrata aislada y no tiene acceso a `Astro.currentLocale` del servidor.
4. **Qué hace fallar el build:** `en.ts` usa `satisfies typeof import('./es').default` — una clave faltante o mal tipada en el diccionario inglés rompe el build. `npm run build` ejecuta `astro check` antes de `astro build`, así que un error de tipos tampoco llega a generar HTML.

### Qué queda fuera de i18n y por qué

- **Toda la Store (`/store/*`)** — decisión de negocio explícita: se traduce solo si la empresa se expande a mercados donde el inglés sea necesario para vender (hoy el negocio es 100% hispanohablante).
- **El catálogo de Envases (`/envases/*`)** — aplazado porque `packagingCatalog.ts` va a migrar a una base de datos real pronto; traducir ahora en `Localized<T>` sería trabajo desechable (el idioma tendría que vivir en el esquema de la base de datos, no en TypeScript). Ver `docs/ESTADO.md` sección 2 para el análisis completo, incluyendo la consecuencia para el diseño de esa base de datos.

### Criterio sobre elementos no disponibles

**Nada se renderiza en vez de un botón deshabilitado o un "próximamente".** Aplica de forma consistente en todo el proyecto: el `LanguageSwitcher` no aparece en páginas sin traducir, el botón de visor 360° no aparece en subproductos sin panorámica, los CTAs de descarga de PDF no aparecen si el archivo no existe en disco (`src/utils/pdfExists.ts`). Un botón roto o un aviso genérico es peor que no ofrecer la acción.

### El flag de la Store y su reversibilidad

`src/config/storeFlags.ts` exporta `STORE_CATALOG_LIVE` (hoy `false`). Es el **único** punto de control para apagar/encender el catálogo de la Store (126 productos con datos de relleno — imágenes de stock, precios simulados). Cambiarlo a `true` restaura navegación con submenús, las rutas dinámicas de catálogo, y los CTAs corporativos hacia la Store — **sin tocar ningún otro archivo**. Nada se borró para apagarlo; no se debe borrar nada para apagar o encender esta u otra funcionalidad detrás de un flag equivalente en el futuro. Ver `docs/ESTADO.md` (sección "Store oculta temporalmente") para el checklist completo de qué vuelve exactamente.

### No inventar especificaciones de producto

**Nunca inventes materiales, garantías, cifras técnicas o cualquier especificación de un producto o servicio real de Asiaven.** Este proyecto publica contenido comercial de una empresa real — una especificación inventada es una afirmación falsa firmada por Asiaven, no un placeholder inocuo. Si falta un dato: deja un marcador explícito (ej. "[confirmar con el cliente]") o pregunta antes de redactar, nunca rellenes con algo plausible.

- Precedente donde esto salió mal: se agregaron features inventadas sin aprobar a "Ascensores de Lujo" (iluminación LED de diseño, panel táctil, "piedra natural" y otros materiales concretos sin confirmar) — el dueño del proyecto las rechazó y hubo que retirarlas.
- Precedente donde el dato inventado resultó correcto y el dueño lo confirmó después (descripción de la división "AV Envasados", que mencionaba envases de aluminio sin que nadie lo hubiera confirmado): **la regla se mantiene igual pese a ese acierto** — el criterio no es "si suena plausible", es "si alguien lo confirmó".

### Formato del "RESUMEN PARA DESARROLLADORES"

**Para qué sirve:** es el bloque de cierre que se le entrega al dueño del proyecto al terminar una tarea. Le permite auditar si la tarea se completó bien **sin tener que revisar el repositorio él mismo** — el resumen debe bastar por sí solo para decidir si algo quedó pendiente, qué se decidió sin que él lo pidiera explícitamente, y qué requiere su decisión. Se usa consistentemente al cerrar tareas en este proyecto; documentarlo aquí es lo que hace que sobreviva a una compactación de sesión.

**Cuándo se usa:** al cerrar cualquier tarea no trivial, salvo que el prompt de la tarea indique explícitamente otro formato de cierre.

**Secciones, en este orden:**

1. **Estado** — una palabra o frase corta: `completado`, `completado con pendientes`, `bloqueado`, etc.
2. **Tarea** — una o dos frases describiendo qué se pidió, para que el resumen sea legible sin releer el prompt original.
3. **Archivos creados** — lista, o "ninguno".
4. **Archivos modificados** — lista, o "ninguno".
5. **Archivos eliminados** — lista, o "ninguno".
6. **Decisiones tomadas no especificadas en el prompt** — cualquier elección hecha sin instrucción explícita (nombres de variables no importan; sí importan decisiones de diseño, redacción de copy, elección entre alternativas técnicas).
7. **Desviaciones del prompt** — cualquier punto donde lo entregado no es exactamente lo pedido, y por qué.
8. **Verificaciones ejecutadas** — qué se corrió para confirmar que funciona (build, greps, pruebas en navegador), con resultados concretos (cifras, hrefs, conteos) en vez de "se verificó que funciona".
9. **Deuda técnica o TODOs dejados** — qué queda pendiente o imperfecto a propósito, y por qué no se resolvió en esta tarea.
10. **Requiere decisión humana** — preguntas abiertas que el asistente no puede ni debe decidir por su cuenta (naming de producto, aprobación de copy, prioridades de negocio).
11. **Estado del repo** — branch actual, si el árbol está limpio, si hay commits pendientes de push/merge.

Si una tarea puntual pide explícitamente un formato de cierre distinto, ese formato tiene prioridad — esta plantilla es el default, no una camisa de fuerza.

## Development

When starting the dev server, use background mode:

```
astro dev --background
```

Manage the background server with `astro dev stop`, `astro dev status`, and `astro dev logs`.
